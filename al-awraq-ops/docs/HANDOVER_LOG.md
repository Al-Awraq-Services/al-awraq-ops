Revisit only if a concrete limitation is found — not a stopgap to be silently replaced.
- **Bug found and fixed during this phase**: the first version of `src/lib/auth/password.ts` exported `MIN_PASSWORD_LENGTH` alongside the argon2 hashing functions. `SetPasswordForm.tsx` (a Client Component) imported that constant, which pulled the entire module — including the native argon2 binary import — into the browser bundle. `npm run build` failed with a real, concrete error (`Module not found: Can't resolve '@node-rs/argon2-wasm32-wasi'`). Root cause: server-only code was reachable from client code through a shared constant. Verified fixed: `npm run build` passed cleanly afterward. See Part 4 below.
- Risks: server-side authorization now exists and is the real attack surface starting this phase — every Server Action re-derives the user/role from the session, never from client input (`requireRoleForAction`), consistent with Phase 4 §5.

- **Mass-assignment prevention, explicit**: `createServiceAction`/`updateServiceAction` build the Prisma `data` object field-by-field from validated zod output via a shared `toWriteValues()` helper — never a spread of raw `FormData` — so a forged extra field (e.g. `isActive=true`, `createdByUserId=...`) submitted alongside a legitimate form post can never reach the database. `isActive` is deliberately absent from `toWriteValues()`; it is only ever set by `deactivateServiceAction`.
- **Audit design**: same pattern as C2/C3 — `SERVICE_UPDATED` logs changed field names only (via a comparable-values diff that normalizes Prisma `Decimal`/`Date` types before comparing, since neither compares correctly with `!==` against the plain number/Date zod produces), never the price value, description content, or price-source text. `SERVICE_CREATED`/`SERVICE_DEACTIVATED` log the service name only, same precedent as `CUSTOMER_CREATED`/`CUSTOMER_ARCHIVED`.
- **Verification-enablement action taken and disclosed in full, not silently done**: this is a fresh session with no active authenticated browser session and no prior knowledge of the seeded Admin's password (set interactively by the developer in an earlier session, never written to any doc, as designed). ### Invoicing — auto-generated on Quote approval (2026-09-13)
- **Context and the prerequisite gap, named before any code was written**: the developer asked for invoicing to trigger "for every job done, or/and quotation approved," with a "button on the side of the Job description" to view it. **Job does not exist in this codebase** — still Phase D2/D3, explicitly listed as unbuilt in every prior phase's scope notes — so there is no "Job description" screen to put a button beside. This was said directly before any scoping began. Two scoping questions were then asked and answered: (1) skip Job for this pass, wire invoicing to **Quote approval only**; (2) "automatically generated" means a real automatic trigger — the moment a Quote is marked Approved, an Invoice is created server-side in the same transaction, not a separate "generate" button.
- **Two deviations from earlier sponsor-approved/precedent decisions, both developer-directed here and disclosed, neither silent**: (1) the Phase 3/5 sponsor-approved "Quote lifecycle: DRAFT, SENT only" (`docs/OPEN_DECISIONS.md`) now has a third status, `APPROVED`; (2) Quote's C3/D1 "remains editable at every status — no lock" precedent no longer holds once a Quote reaches `APPROVED` — see below for why, and see `docs/OPEN_DECISIONS.md` for the disclosure.
- **Schema** (`prisma/schema.prisma`, migration `20260913090343_invoicing`, additive only — confirmed via the generated SQL, no existing table altered): `QuoteStatus` gained `APPROVED`; new `Invoice` model (`sequenceNumber` — a separate autoincrementing int purely for a human-readable `INV-000123` number, distinct from the cuid `id`; `status: PaymentStatus` — `UNPAID`/`PAID`; `quoteId @unique` — exactly one Invoice per Quote, enforced at the database level, not just in application code; `customerId`, `createdByUserId`, `paidAt`); new `InvoiceItem` model — a **frozen snapshot** of each QuoteItem at the moment of approval (same shape minus `serviceId`, which is a catalog-traceability concern for an in-progress Quote, not a finished document). No stored total on either — same "compute live from items" pattern already established for Quote/QuoteItem, safe here specifically because `InvoiceItem` rows are themselves immutable (no update action exists for them anywhere in the codebase — that absence is the actual enforcement of "an invoice can't change after the fact," not just a comment).
- **Why Quote gets locked at Approved, stated plainly since it reverses an earlier precedent**: once an Invoice exists, it's copied data — if the Quote's own customer/notes/line items kept changing afterward, the Invoice would silently stop matching the record it was supposedly generated from. `requireQuoteEditable` (`src/actions/quotes.ts`) is the single enforcement point — every mutating Quote/QuoteItem action (`updateQuoteAction`, `addQuoteItemAction`, `updateQuoteItemAction`, `removeQuoteItemAction`) calls it first and returns/throws a clear error if the Quote is already Approved. The Quote detail page reflects this the same way an archived Customer or deactivated Service already does: a read-only summary instead of the form, read-only line items instead of the editable rows.
- **The approval transaction** (`updateQuoteAction`): when the submitted status is `APPROVED` and the existing status isn't, the action first requires at least one `QuoteItem` to exist (rejects with "Add at least one line item before approving this quote." otherwise — approving nothing to invoice doesn't make sense) — a new business rule, not previously specified, added here and disclosed. If that passes, within the same `db.$transaction` as the status update: every current `QuoteItem` is read and copied into new `InvoiceItem` rows under a new `Invoice`, and an `INVOICE_CREATED` audit row is written (`metadata: { quoteId }`, no financial figures logged, consistent with every other audit entry's PII/value-avoidance discipline). The `quoteId @unique` constraint is a second, database-level backstop against ever double-invoicing the same Quote, on top of the application-level lock.

## Part 4 — Bugs and Fixes

### Bug: server-only password module reachable from a Client Component (Phase B)
- Symptom: `npm run build` failed — Turbopack could not resolve `@node-rs/argon2-wasm32-wasi` and reported "Export hash/verify doesn't exist in target module" for a browser bundle.
- Root cause: `src/lib/auth/password.ts` (imports the native argon2 binary) also exported a plain constant, `MIN_PASSWORD_LENGTH`, that a Client Component (`SetPasswordForm.tsx`) imported for a `minLength` attribute — pulling the whole server-only module into the client bundle.
- Fix: moved the constant to a new dependency-free file, `src/lib/validation/constants.ts`; added `import "server-only"` to every server-only auth/audit module so a repeat of this mistake fails the build immediately with a clear error instead of a confusing bundler resolution failure.
- Verification: `npm run build` re-run after the fix, completed successfully with all 7 routes generated correctly (see Phase B test checklist).

### Bug: `prisma/seed.ts` crashed under `tsx` due to `server-only` guards (Phase B)
- Symptom: `npm run db:seed` failed immediately with `Error: This module cannot be imported from a Client Component module. It should only be used from a Server Component.`, thrown by the `server-only` package.
- Root cause: `prisma/seed.ts` imported `unusablePasswordHash` from `src/lib/auth/password.ts` and `generateRawToken`/`hashToken` from `src/lib/auth/tokens.ts` — both files are guarded by `import "server-only"` (added deliberately in Phase B to stop a different, earlier bug — see the entry above — from recurring). That guard only works inside Next.js's build pipeline, which sets a special condition it checks for. `prisma db seed` runs the script standalone under `tsx`, which never sets that condition, so the guard throws unconditionally, even though a CLI seed script is a legitimate server-side context.
- Fix (sponsor-approved, minimal, single file): `prisma/seed.ts` no longer imports from either guarded module. It now contains its own small, duplicated copies of the three needed functions (`unusablePasswordHash`, `generateRawToken`, `hashToken`), using the same underlying libraries (`@node-rs/argon2`, `node:crypto`) directly. `src/lib/auth/password.ts`, `src/lib/auth/tokens.ts`, and `src/actions/users.ts` were left completely untouched — the `server-only` guards protecting real app code from ever reaching a browser bundle remain fully intact.
- Verification: `npm run db:seed` re-run after the fix — succeeded, created the first Admin, printed a one-time setup link. No other command was run in that step (no migration, no dev server).

### Bug: Prisma `Decimal` objects passed into a Client Component (Phase D1)
- Symptom: every load of `/quotes/[quoteId]` logged four browser console errors — "Only plain objects can be passed to Client Components from Server Components. Decimal objects are not supported."
- Root cause: `quotes/[quoteId]/page.tsx` fetched active services with `db.service.findMany({ where: { isActive: true } })` (full rows, including the `Decimal` `placeholderPrice` field) and passed the result straight into the `QuoteItemForm` Client Component, which only ever used `id`/`name`.
- Fix: added `select: { id: true, name: true }` to that query, so only plain, serializable fields cross the Server→Client boundary.
- Verification: reloaded the page after the fix, confirmed zero console errors (previously 4 on every load).

### Bug: stale `<select defaultValue>` silently reverts on a second save — affects Quote (new) and Lead (already-shipped Phase C3) (Phase D1)
- Symptom: change a Quote's or Lead's status via its edit form's dropdown, save (correctly persisted — confirmed via the page header and the database), but the dropdown itself visually reverts to the pre-change value in that same render. Clicking "Save changes" again **without touching the dropdown** silently writes the old status back — a real, silent data-revert risk, not cosmetic.
- Root cause: `<select defaultValue={...}>` is only applied by React at mount. After a Server Action's `revalidatePath` triggers a re-render with fresh server data (not a full page navigation), the already-mounted `<select>` DOM node is not reliably reset to the new `defaultValue`, so it can display — and then resubmit — stale data even though the rest of the page's freshly-rendered content is correct.
- Discovered in the new `QuoteForm`; confirmed to be a pre-existing, previously-undetected defect in the already-shipped `LeadForm` too (identical pattern, identical repro). It went undetected in C3/C5 verification because those sessions happened to reload the page between checks, which coincidentally re-initializes `defaultValue` correctly and masks the bug.
- Fix: gave each affected form component a React `key` derived from the record's current editable-field values (e.g. `key={`${quote.customerId}|${quote.leadId}|${quote.notes}|${quote.status}`}`), forcing a full remount — and therefore a correct `defaultValue` re-initialization — whenever the underlying record changes. Applied to `QuoteForm` (`quotes/[quoteId]/page.tsx`), each `QuoteItemForm` row and the "add a line" form, and `LeadForm` (`leads/[leadId]/page.tsx`).
- Verification: repeated the exact "change status → save → save again untouched" sequence on both the Quote and the Lead screens after the fix; confirmed the status now correctly holds across the second save in both the UI and the database. The Lead test record's status was restored to its original value (`NEW`) afterward.

### Bug: stale Prisma Client in an already-running dev server after a migration (Public request-a-quote pass)
- Symptom: the first live submission of the new public form failed with `PrismaClientValidationError: Invalid value for argument 'source'. Expected LeadSource.`, even though `WEBSITE` had already been added to the `LeadSource` enum in `schema.prisma` and the migration adding it had already been applied.
- Root cause: `next dev` had been running continuously since before the schema change. `prisma migrate dev` regenerates the Prisma Client on disk, but a Node process that already imported the old generated client keeps the old module in memory — a fresh `import` doesn't happen just because the files on disk changed, since Node's module cache (and Turbopack's own compiled-chunk cache) aren't the same thing as "the source changed."
- Fix: not a code change — stopped and restarted the dev server process so it re-imported the freshly generated client.
- Verification: the identical form submission that failed before succeeded cleanly after the restart; confirmed via the database that the Lead and its audit row were both written correctly.

### Bug: header nav overflows and clips "Sign out" off-screen on mobile widths (UI/Branding pass)
- Symptom: at a 375px viewport, the internal-layout header's single row (logo + nav links on the left, user info + Sign out on the right, `justify-between`, no wrap) had no room for the full nav — "Sign out" was pushed past the visible right edge.
- Root cause: no responsive behavior had been designed for the header at all; it assumed enough width for the logo, up to six nav links, the user's name/role, and Sign out all on one line.
- Fix: restructured `src/app/(internal)/layout.tsx`'s header into two rows — identity + role badge + Sign out on top (always visible, `justify-between`), nav links below in a horizontally-scrollable strip (`overflow-x-auto whitespace-nowrap`). A proportionate fix, not a full hamburger-menu mobile nav, since no mobile-first requirement was ever stated for this internal tool.
- Verification: re-checked at 375px via `resize_window` — Sign out fully visible, nav scrolls cleanly with no overflow.
