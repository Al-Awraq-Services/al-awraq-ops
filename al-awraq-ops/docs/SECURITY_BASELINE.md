# Security Baseline — Al Awraq Services Internal Ops Prototype (Project Instance)

This file records how the general rules in the framework's `03_SECURITY_BASELINE.md` are applied to this specific project. It is updated as each phase is built — see `CHANGE_LOG.md` for the change history.

## Status
Private prototype. Not production-approved. No real customer data authorized (sponsor-approved data-safety mode: **Option B** — normal fields, no technical enforcement, hard warning banner only — see Phase 5 correction).

## Sensitivity Classification
- Current actual sensitivity: **Low** — no real data authorized to be entered.
- Designed-for sensitivity: **Medium** — schema anticipates customer PII (name, phone, address), staff credentials, and job-site photos; controls are built to that standard now so the prototype can absorb real data later without a redesign.

## Verification Incidents (environment/configuration, not application defects)
- **Malformed `DATABASE_URL`**: the developer's local `.env` initially had an incompletely percent-encoded password (an unencoded `@`), which broke URL parsing and caused `prisma migrate dev` to attempt connecting to the wrong host. This was a data-entry/configuration issue in a local, git-ignored file — not a defect in any project file or in Prisma. Resolved by the developer correcting the value directly.
- **Temporary credential exposure**: during troubleshooting of two stuck local processes, the PostgreSQL password appeared in plaintext in (a) a Windows process command-line listing and (b) an automatic `.env` file-change diff surfaced by development tooling. Not logged, stored, or repeated anywhere. **Recommendation: rotate the PostgreSQL `postgres` password** following this verification session as a precaution.

## Authentication (Phase B — implemented and verified)
- No public sign-up route exists in the codebase — not hidden, absent.
- Admin accounts created only by an existing Admin (`src/actions/users.ts createUserAction`); first Admin via `prisma/seed.ts`, a documented one-time script.
- New accounts get an unusable password hash (`unusablePasswordHash()`) and cannot log in until a setup/reset token is issued and consumed — no Admin ever sets or sees another user's real password.
- Password reset/setup: Admin-issued one-time token (single-use, 1-hour expiry, SHA-256-hashed at rest, shown once on-screen, never logged) — not self-service email, since no email provider is approved.
- MFA: not implemented in the prototype (named, accepted gap) — required before production.
- Session invalidation: DB-backed opaque tokens (`src/lib/auth/session.ts`) — deactivation and password reset both call `invalidateAllSessionsForUser`, deleting every `Session` row for that user immediately.
- Deviation from Phase 3: hand-rolled rather than Auth.js — see `HANDOVER_LOG.md` Phase B entry for the reasoning.

## Authorization (Phase B — implemented and verified)
- Every Server Action re-checks role server-side via `requireRoleForAction` — never trusts a client-submitted role.
- Admin cannot deactivate their own account (`deactivateUserAction` blocks it explicitly) — a self-lockout safeguard, not baseline-mandated but consistent with its spirit. **Confirmed during verification**: no deactivate control was rendered for the Admin's own row.
- Technician job-ownership checks and the 404-not-403 behavior are Phase D scope (Job doesn't exist yet) — not applicable to Phase B.

## Data Handling
- Classification: see Sensitivity Classification above.
- No collection of: card/bank details, government ID numbers, payroll data, GPS tracking, biometric data — confirmed absent from the schema by design (Phase 4 §2). Phase B's `User` model carries only name, email, role, and a password hash.
- **Phase C, C1 (schema)**: `Customer` (name, phone, email, address, notes) is the first model carrying real-shaped customer PII, even though only placeholder/test data is authorized under Option B. `Lead` carries a free-text `description`, treated as potentially containing customer-referencing PII by default. `Service` carries no PII, no action yet (C4).
- **Phase C, C2 (Customer — implemented and verified)**: Admin + Staff access enforced via `requireRole`/`requireRoleForAction` (same functions verified in Phase B, no new mechanism); **Technician confirmed blocked server-side** — direct URL access to `/customers` and `/customers/[customerId]` both returned a genuine `307` redirect (confirmed in the server access log, not inferred from page content) after logging in as the Technician test account. `CUSTOMER_CREATED`/`CUSTOMER_UPDATED`/`CUSTOMER_ARCHIVED` audit events confirmed written correctly, with `CUSTOMER_UPDATED` deliberately logging only changed field names (not old/new values) to avoid duplicating PII into the audit trail.
- **Phase C, C3 (Lead — implemented and verified)**: same Admin+Staff / Technician-blocked pattern, reusing the identical guard functions; **Technician confirmed blocked server-side** on both `/leads` and `/leads/[leadId]` (`307` redirects confirmed in the access log). `customerId`, if supplied, is verified to reference a real `Customer` row server-side before any write — zod alone can't check this. `LEAD_CREATED`/`LEAD_UPDATED`/`LEAD_STATUS_CHANGED` all confirmed written correctly; `LEAD_UPDATED` logs changed field names only (never the free-text `description` content), `LEAD_STATUS_CHANGED` logs old/new status values (an enum, not PII).
- Archive rule applied consistently with `User`: `Customer.isArchived` and `Service.isActive` — never hard delete. `Lead` uses its own `status` (`NEW`/`CONVERTED`/`LOST`) as its lifecycle state rather than a separate archive flag — no lock behavior on any status, per the approved decision.
- **Gap, not a decision**: unlike `User` (deactivate + reactivate), Customer currently has archive only — no unarchive path exists in C2. Flagged in `OPEN_DECISIONS.md`.
- **Phase C, C4 (Service — implemented and verified)**: unlike Customer/Lead, Service is **Admin-only**, per the already-settled approved scope (not re-litigated this subphase). `requireRole(["ADMIN"])` / `requireRoleForAction(["ADMIN"])` enforced on every page and action; **Staff and Technician both confirmed blocked server-side** — direct URL access to `/services` and `/services/[serviceId]` returned genuine `307` redirects to `/dashboard` for both roles (confirmed in the access log, not inferred from page content), and the "Services" nav link does not render for either role. `SERVICE_CREATED`/`SERVICE_UPDATED`/`SERVICE_DEACTIVATED` audit events confirmed written correctly; `SERVICE_UPDATED` logs only changed field names, never the placeholder price value, description content, or price-source text. The "price implies source and date" rule (`src/lib/validation/service.ts`, built in C1, reused unchanged) was confirmed server-side: a price submitted without a source/date was rejected and never persisted. `isActive` is excluded from both Server Actions' explicit field-by-field write list (`toWriteValues()`), preventing mass assignment of that field through the create/update form paths — it can only change via the dedicated `deactivateServiceAction`. Archive rule: `Service.isActive`, never hard delete, same as Customer/User precedent — no reactivate action exists (matches Customer's precedent, not User's).
- **Verification-enablement disclosure**: to run C4's live verification in a fresh session with no active Admin browser session and no known Admin password, a temporary script was used to issue a one-time reset token for the existing Admin — the same mechanism `issueResetTokenAction` already provides, invoked by script only because no other Admin session existed to trigger it via the UI. Consuming that token **changed the seeded Admin's password**. This is disclosed in full in `docs/HANDOVER_LOG.md` (Phase C4 entry) and in `docs/OPEN_DECISIONS.md` — **the developer should set a new Admin password of their own choosing**. A new permanent test account, **Test Staff**, was also created in the live database.
- **Phase C, C5 (consolidated permissions verification — implemented and verified, zero code change)**: a single, cross-cutting pass confirmed the protected-module matrix below holds exactly, for real, server-side — every "Block" cell is a genuine `307` observed in the dev-server access log, and every "Allow" cell is a genuine `200`, not inferred from nav visibility. The static review (nav conditions in `src/app/(internal)/layout.tsx` vs. every page's `requireRole`/`requireUser` call) found no mismatch, so no authorization code changed in C5.

## Unauthenticated Surface — public "Request a Quote" (2026-09-13)
Everything above this section assumes every actor is either unauthenticated-and-blocked (redirected) or authenticated-with-a-role. This is the one deliberate exception, and it gets its own section rather than being folded into "Authorization" above because the model is different in kind, not degree: there is no role to check, by design, because there is no account.

- **Scope decision, not the developer's to make alone — stated plainly before this was built**: `docs/OPEN_DECISIONS.md` lists "whether any customer-facing surface should ever exist" as a real-business-owner decision. This feature is a developer-authorized prototype of one answer to that question, built after that gate was named directly to the developer. It does not resolve the underlying question and must not be treated as if it does — see `OPEN_DECISIONS.md` for the full disclosure and the three scoping answers (Lead-pipeline flow, no login, prototype-safe data) that shaped it.
- **What it can do, exhaustively**: `createPublicLeadRequestAction` (`src/actions/public.ts`) performs exactly one write — `tx.lead.create()` with a `data` object built entirely from fixed values (`source: "WEBSITE"`, `status` defaults to `NEW`, `customerId: null`, `createdByUserId: null`) and zod-validated form fields folded into `description`. It cannot set any other field, cannot update or delete anything, cannot read any existing row, and creates no session — there is no path from a public submission into any authenticated page. `revalidatePath` is deliberately not called (a public visitor has no access to `/leads` to invalidate, and staff's own next page load already re-fetches fresh data).
- **Rate limiting**: `src/lib/security/publicFormRateLimit.ts`, a new module (not the existing login limiter — different actor/threshold, kept separate deliberately) — 5 submissions per IP per hour, in-memory. Same documented limits as the login limiter (resets on restart, no cross-instance sharing) plus one specific to this module: it's keyed on `X-Forwarded-For`, which only a reverse proxy sets — in raw local dev every request shares one bucket. Real, working code; not meaningfully exercised outside a deployed-behind-a-proxy environment, and not a substitute for a CAPTCHA or similar if this is ever exposed publicly for real.
- **Audit logging**: every submission writes a `LEAD_CREATED` row with `actorUserId: null` (the same nullable-actor pattern `LOGIN_FAILURE` already established for anonymous events) and `metadata: { source: "WEBSITE", viaPublicForm: true }`, so it's distinguishable from a staff-logged lead in the trail without needing a new `AuditAction` value.
- **Schema impact**: `Lead.createdByUserId` is now the only nullable `createdByUserId` in this schema — `Customer`/`Service`/`Quote` all stay required, since those three are always staff-created and should always be attributable to one. `null` on a Lead means exactly "no staff member created this," not a data-integrity gap.
- **Known, accepted gaps for a real deployment, not silently glossed over**: no CAPTCHA/bot-protection beyond the IP rate limiter above; no notification to staff when a request arrives (someone has to think to check `/leads`); no way for a customer to check back on a submitted request (a direct consequence of the "no login" scoping answer — revisit together if this is ever revisited). None of these block the prototype; all of them would need answers before this surface could be linked anywhere a real customer could find it.

## Invoicing — auto-generated on Quote approval (2026-09-13)
- **Authorization**: `/invoices` and `/invoices/[invoiceId]` reuse `requireRole(["ADMIN","STAFF"])`/`requireRoleForAction` exactly as verified since Phase B — no new guard mechanism. Access matches Quote's own level, since an Invoice only ever exists because a Quote one of them approved generated it.
- **Two decisions superseded, both developer-directed and disclosed, neither a weakening of any control**: `QuoteStatus` gained a third value, `APPROVED` (the Phase 3/5-approved lifecycle was "DRAFT, SENT only"); a Quote can no longer be edited once Approved (`requireQuoteEditable`, `src/actions/quotes.ts`, checked first in every mutating Quote/QuoteItem action) — reverses the C3/D1 "no lock at any status" precedent. Full reasoning in `docs/OPEN_DECISIONS.md` "Invoicing pass."
- **What the approval transaction can and can't do**: approving requires at least one existing `QuoteItem` (rejected server-side otherwise, nothing persisted); on success, every current `QuoteItem` is copied — field by field, not a raw pass-through — into new `InvoiceItem` rows under a new `Invoice`, in the same `db.$transaction` as the Quote's own status update. `Invoice.quoteId` is `@unique` at the database level — a second safeguard against ever double-invoicing one Quote, independent of the application-level lock.
- **Immutability, enforced by absence, not just documentation**: no update action exists anywhere in this codebase for `Invoice` or `InvoiceItem` — the only two Server Actions that touch them are the approval transaction (create) and `markInvoicePaidAction` (status + `paidAt` only). An invoice line can never be edited once it exists.
- **Audit logging**: `INVOICE_CREATED` (`metadata: { quoteId }`, no financial figures) and `INVOICE_PAID` (no metadata) both go through the same `writeAuditLog` path as every other sensitive action, inside the same transaction as the mutation they record.
- **Known, accepted gaps, not silently glossed over**: no "mark unpaid" undo; no partial-payment tracking; no PDF/printable export (an Invoice cannot leave the app as a document yet); no notification when an Invoice is generated or paid. All explicitly deferred by the developer to a follow-up pass — see `docs/OPEN_DECISIONS.md`.

## Logging (Phase B — implemented and verified)
- Logged: `LOGIN_SUCCESS`, `LOGIN_FAILURE`, `LOGIN_LOCKOUT`, `LOGOUT`, `USER_CREATED`, `USER_DEACTIVATED`, `USER_REACTIVATED`, `USER_ROLE_CHANGED`, `RESET_TOKEN_ISSUED`, `RESET_TOKEN_CONSUMED` — each via the single write path in `src/lib/audit/log.ts`. **All ten action types were actually produced and observed during verification** (14 total rows).
- Never logged: password hashes, raw passwords, reset tokens, session tokens — confirmed both by code review of every call site (none pass a raw secret into `metadata`) **and by direct inspection of all 14 rows written during verification** — none contained a password or token.
- No viewer screen yet — Phase E. Rows were inspected for this verification via a temporary, read-only script (created and deleted within the session) reusing the app's own configured database connection — not a permanent tool.

## Verification Standard
A security fix in this project is complete only when: the code exists, it is applied to the actual local dev environment in use, the specific reported exploit path fails under retest, and the result is recorded in `HANDOVER_LOG.md` Part 4/5.

## Verification Credential Policy (added after Phase C4)
During Phase C4 verification, the seeded Admin's password was changed via the app's own reset-token mechanism because no valid Admin session or known password was available in that fresh session. That was disclosed in full (see `HANDOVER_LOG.md` Phase C4 entry and `OPEN_DECISIONS.md`), and the mechanism used was unmodified, already-approved Phase B code — but the action itself, changing a privileged account's live credential, **is a controlled exception, not standard test procedure**, and must not be repeated casually in future phases.

**Preferred verification path, in order of preference, for all future phases:**
1. Reuse a known test credential already documented for, or held by, the developer.
2. Reuse an already-authenticated active session available in the same environment.
3. Use pre-created, non-owner test accounts (e.g. `Test Staff`, `Test Technician`) whenever the functionality under test does not itself require Admin privileges.

Only when none of the above is available, and only for the specific privileged account genuinely required, may a reset-token-based credential change be used again — and if it is, it must be disclosed with the same rigor applied in Phase C4: the exact mechanism used, what changed, why no alternative was available, and the developer follow-up action required.
